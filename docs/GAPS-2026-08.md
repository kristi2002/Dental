# What is still missing — a fresh read, August 2026

The three documents already in this folder each answer a different question.
[IMPROVEMENTS.md](IMPROVEMENTS.md) says what is wrong with the code that exists.
[ROADMAP.md](ROADMAP.md) says what does not exist yet — and every phase in it now
reads *implemented*. [APP-BLUEPRINT.md §8](APP-BLUEPRINT.md#8-gap-register) keeps
a register of loops that cannot close, and it is almost entirely ticked.

So the honest answer to "what else is missing" is not in any of them. This
document is a fresh pass over the repository as it actually stands at commit
`c2a3ac5`, and most of what it finds is not in the domain at all. The clinical
model is in good shape. What is missing is everything around it: the build does
not build, the migrations no longer describe the schema, nothing runs the tests,
and the app has no behaviour at all for the moment something throws.

Findings are ordered by what they cost, not by how hard they are.

**Legend** — 🔴 broken now · 🟠 will break · 🟡 scale · ⚪ operational

---

## 1. The production image cannot be built

### 1.1 🔴 `npm ci` fails — the lockfile is out of sync with `package.json`

```
$ npm ci
npm error Missing: @swc/helpers@0.5.23 from lock file
```

`package-lock.json` has no `node_modules/@swc/helpers` entry, but the installed
tree needs one — Next 16 pulls it in. `npm ci` refuses to guess, and refusing is
the whole point of `npm ci`.

[Dockerfile:44](../Dockerfile) is `npm ci`. So **the production image does not
build**, and has not since whatever change last touched the dependency tree
without regenerating the lock. `npm install` masks it locally, which is exactly
why nobody noticed: development works, deployment does not.

**Fix.** `npm install && git add package-lock.json`. Verified: after that,
`npm ci` succeeds and the resulting tree runs typecheck, lint and the full test
suite clean. It adds 32 lines to the lockfile and nothing else.

That this is a one-command fix is not the interesting part. The interesting part
is §1.4 — nothing in this repository would ever have told you.

### 1.2 🔴 The migration history stopped describing the schema nine commits ago

The blueprint says the schema is under migration control and that
`npm run db:deploy` is the release step. The last migration written is
`20260814000002_template_services_drop_lab`. Since the commit that added it,
**nine commits have changed `prisma/schema.prisma`** and none has added a
migration:

```
c2a3ac5 feat: implement dental charting system …
9c0a08a feat(audit): drill through from a line in the trail …
46baf05 feat(audit): keep the activity log queryable …
8338fb0 fix: close eight logic and table-connectivity gaps …
9670030 feat(auth): implement idle session lock and unlock …
f7b2de1 feat: add follow-ups management module …
2b21a1e feat: add material history and scanner functionality
f14592d feat: add new work management forms and functionality
53b5d90 feat(stock): add stock categories, new stock item, and suppliers …
```

Three whole models exist in the schema and in no migration at all:

| Model | in `schema.prisma` | in `prisma/migrations/` |
| --- | :-: | :-: |
| `FollowUp` | ✅ | ❌ |
| `WorkProcedure` | ✅ | ❌ |
| `ProductBarcode` | ✅ | ❌ |

A practice that follows the documented release step gets a database with no
follow-up board, no work-procedure catalogue and no barcode table — against an
application that queries all three on its dashboard. It does not degrade; it
throws.

**Fix.** One `migrate diff --from-config-datasource` against the last applied
migration, checked in as a numbered migration, and then §1.4 to keep it from
happening again.

### 1.3 🔴 …and the container never uses migrations anyway

[docker/entrypoint.sh](../docker/entrypoint.sh) opens with:

> The project keeps no migration history — `prisma db push` is its workflow

and runs `prisma db push` on every boot. That is the opposite of what
[README.md:202](../README.md) and the blueprint both say, and it is why §1.2 has
gone unnoticed: `db push` reads the schema file directly, so a deploy is always
correct and the migration folder is decoration.

This matters beyond tidiness. `db push` has no history, so there is no rollback,
no record of when a column appeared, and no reviewed SQL for a change that
rewrites data. The entrypoint's own comment concedes the sharpest edge — it runs
without `--accept-data-loss` so a destructive change *stops the deploy*, at which
point somebody has to hand-resolve a production database at eight in the morning.
That is precisely the situation migrations exist to prevent.

Pick one and make the repository say it once. Either:

- **migrations win** — entrypoint runs `migrate deploy`, `_prisma_migrations` is
  baselined against the existing production database, and §1.2 is closed first
  (deploying `migrate deploy` against a `db push`-shaped database without
  baselining will try to re-run `0_init` and fail); or
- **`db push` wins** — delete `prisma/migrations/`, drop `db:deploy` from
  `package.json`, and correct the two documents. Defensible for a single-clinic
  install, and at least it would be true.

The current state is the worst of both: the cost of maintaining migrations, none
of the benefit, and two documents describing a release step nobody runs.

### 1.4 🟠 There is no CI. None.

There is no `.github/` directory. Nothing runs `npm run typecheck`, `npm run
lint` or `npm test` on a push. Every finding in §1 is a thing a five-line
workflow would have caught the day it was introduced:

```yaml
# .github/workflows/ci.yml
- run: npm ci                       # catches 1.1
- run: npx prisma migrate diff \
    --from-migrations prisma/migrations \
    --to-schema-datamodel prisma/schema.prisma \
    --exit-code                     # catches 1.2
- run: npm run typecheck && npm run lint && npm test
```

For a project carrying 374 tests, an oxlint config and a `typecheck` script, the
absence of anything that runs them is the single highest-leverage gap in the
repository.

### 1.5 🟠 A fresh clone cannot install

`postinstall` runs `prisma generate`, and [prisma.config.ts](../prisma.config.ts)
resolves `env('DATABASE_URL')`. On a clone with no `.env` — which is every clone,
since `.env` is gitignored and only `.env.example` ships — that is:

```
Failed to load config file … PrismaConfigEnvError: Cannot resolve environment variable: DATABASE_URL
```

`npm install` exits non-zero. Three test files then fail on
`Cannot find module '@/generated/prisma/enums'`, because the client was never
generated — so `npm test` on a fresh clone reports **3 failing suites that are
not failures**. Set any `DATABASE_URL` and all 374 tests pass.

Generating a client does not need a reachable database, or a real URL. Either
give the datasource a harmless default when the variable is absent, or drop
`prisma generate` from `postinstall` and let `dev`/`build`/`test` depend on it.
Right now the first thing a new contributor sees is a broken install followed by
broken tests, and neither is real.

## 2. Security and the audit trail

The access model is genuinely good — one table, checked in both places, refusals
logged. Every server action calls `authorize()`; the one that does not
(`regenerateCalendarFeed`) is deliberate and argued for. These are the edges
around it.

### 2.1 🟠 A failed PIN leaves no trace

[`checkPin`](../src/lib/actions/auth.ts) increments `failedAttempts`, locks the
account at five, and writes **nothing to the audit log**. `recordAudit` is called
on success only.

In an application whose stated purpose for the activity log is that "a
receptionist repeatedly trying to open the chart is worth seeing", somebody
working through PINs at the reception tablet overnight is worth seeing rather
more, and is the one thing the trail cannot show. The `denied` line exists for
permission refusals; the same line for a wrong PIN, and one for a lockout, is a
handful of lines of code.

### 2.2 🟠 Sign-in is the only unauthenticated surface with no rate limit

`rateLimit()` guards `/confirm/[token]`, `/api/calendar/[token]` and first-run
setup. It does not guard `signIn` or `unlockSession`.

The per-account lockout does bound this — but look at what it bounds it *to*.
On the fifth wrong PIN the code sets `failedAttempts: 0` and a five-minute lock;
when the lock lapses the attacker gets five more. There is no escalation, no
ceiling, and (per §2.1) no record. That is a permanent, undetectable 60 guesses
per hour per account, against a **4-digit** PIN — 10 000 values, so a median hit
in about three and a half days of quiet grinding.

An IP bucket on `signIn` costs one line and the module is already imported for
setup. Escalating lockout (5 min, 30 min, then hold) costs a little more and is
what actually removes the attack.

### 2.3 🟠 No security response headers

[next.config.ts](../next.config.ts) defines no `headers()`, and the repository
carries no reverse-proxy configuration — Coolify terminates TLS and forwards.
So the app ships with no `Content-Security-Policy`, no `X-Frame-Options`, no
`Referrer-Policy`, no `X-Content-Type-Options`, no HSTS.

This is an application that serves radiographs to a browser on a shared
reception machine. The document and photo routes were carefully given
`Cache-Control: private` for exactly that reason; the headers that stop the page
around them being framed, sniffed or leaked via `Referer` were never added.

### 2.4 🟡 Document access is still not scoped to a patient (G-28)

Still open from the blueprint's own register. `/api/documents/[id]` checks that
you may view documents; it does not check *whose*. Anyone signed in with
`document.view` can walk ids. In a four-person clinic the blast radius is small,
which is presumably why it was deferred — but it is the last unscoped read in
the app, and the register has carried it for a while now.

## 3. What the app does when something goes wrong: nothing

### 3.1 🟠 There is no error boundary anywhere

```
$ find src/app -name "error.tsx" -o -name "global-error.tsx"
(nothing)
```

Two `not-found.tsx` files exist and are well done. There is no `error.tsx` at any
level and no `global-error.tsx`. So any throw in any server component — a
database blip, a malformed row, a missing file — renders Next's default error
page: English, unstyled, "Application error: a server-side exception has
occurred", and no way back.

For an app whose entire design brief is large type, high contrast and every
screen doing one obvious thing, aimed at a dentist who trusts pen and paper,
that is the one screen nobody designed. One `error.tsx` in `(app)/`, in the app's
own visual language, with the practice's three locales and a "try again" button,
covers every route in the group.

### 3.2 ⚪ No `loading.tsx`, so every navigation is a dead click

There is no `loading.tsx` anywhere either. Pages are server-rendered against
Postgres with no streaming boundary, so tapping *Patients* on a mini-PC gives no
feedback at all until the whole page is ready. The `Suspense` fallbacks that
`loading.tsx` provides are free — the segment is already there.

## 4. Operations: nothing is scheduled

The deployment has an app container and a Postgres container. It has no
scheduler, no cron, no job runner — and four things that need one.

### 4.1 🟠 Backups are a button somebody has to remember to press

`docs/DEPLOYMENT.md` is honest about this: Coolify backs up managed databases on
Path B; on Path A you "back up the `db-data` volume, or add a scheduled
`pg_dump`", and the patient-files volume is your problem either way. The in-app
export is owner-only and manual.

So on the default path, a clinic keeping seven years of medical records has
exactly the backup discipline of whoever remembers to click. A `pg_dump` sidecar
plus a `tar` of `/data` on a nightly timer is the smallest thing that makes the
7-year retention decision in `audit-retention.ts` mean anything.

### 4.2 ⚪ `prune-audit.ts` has no runner

The entrypoint explains, at some length, that nothing prunes the activity log on
purpose, and points at `prisma/prune-audit.ts` for "the by-hand trim if a
practice ever needs one". Fine as a decision — but it means the script is
untested, unscheduled, and will be reached for exactly once, in a hurry, by
somebody who has never run it.

### 4.3 ⚪ The app container has no healthcheck

`docker-compose.prod.yml` gives `db` a `pg_isready` healthcheck. The `app`
service has none — despite `/api/health` existing, being deliberately
unauthenticated, and being documented as safe to point a monitor at. Four lines
of YAML connect the two.

### 4.4 ⚪ Nothing verifies `storage/` is being copied (G-51)

Still open. The entrypoint does warn loudly when `/data` is not a mounted
volume, which is the sharper half of the problem. The other half — "your backups
have been running for six months and contain no radiographs" — has no check.

## 5. The tests are good and cover the wrong half

374 tests, all passing, no database required. They are genuinely useful — the
blueprint records that they found a real `addMonths` bug on their first run.

They are also **entirely pure-function tests**, and several of the most
consequential pure functions in the app have none:

| Module | Lines | What it decides | Tested |
| --- | ---: | --- | :-: |
| `stock-consumption.ts` | 265 | batch drawdown — the thing that can drive stock negative | ❌ |
| `recalls.ts` | 200 | who is overdue for a check-up, and when | ❌ |
| `reliability.ts` | 106 | the no-show score shown on every patient | ❌ |
| `work-procedures.ts` | 106 | the works catalogue | ❌ |
| `patient-search.ts` | 83 | diacritic folding — the fix for G-18 | ❌ |
| `reminder-messages.ts` | 81 | which language a patient is written to in | ❌ |
| `plan-sync.ts` | 79 | plan step ⇄ appointment, both directions | ❌ |

`patient-search.ts` is the sharp one: G-18 was closed by a fold that has no test,
so the next person to touch it has nothing telling them Albanian *ë* and *ç* must
survive the round trip.

Beyond that, **no test touches a server action or the database.** Every
invariant in the blueprint's Appendix B — stock never negative, a declined
appointment stays declined, completing an appointment ticks its plan step — lives
in code no test exercises, and each of those was a 🔴 bug once already. A
throwaway Postgres in CI (the `docker-compose.yml` already in the repo) plus a
dozen action-level tests would hold the line that §1's whole build problem is
currently not holding.

## 6. Modelling debt still open from IMPROVEMENTS.md

Named here only because these are the items that outlived their document, not to
re-argue them.

| # | | Still true |
| --- | --- | --- |
| 2.2 | 🟠 | `ToothRecord.status`, `AuditLog.action` and `AuditLog.entity` are free-text `String` with the valid values written in a comment |
| 2.3 | 🟠 | `Appointment.startTime` is a `String`, so every scheduling question is answered in JavaScript rather than in Postgres |
| 2.6 | 🟠 | Patients are hard-deleted while staff, services and materials are archived — the one row with a legal retention period is the one with no undo |
| 3.4 | 🟡 | `revalidatePath('/', 'layout')` appears in **17** places; every write anywhere flushes the entire cache |

And one the register never named:

### 6.1 🟠 `WorkLine.lab` is a text reference to an entity that does not exist

The schema argues the case for free text: "a practice sends to two or three labs
whose names it already knows how to spell." Directly below it, `WorkProcedure`
exists because the identical argument was made for `procedure` and then
reversed — a zirconia crown went out as "Kurorë zirkoni", "kurore zirkon" and
"Zirkon" in the same week, and "nothing could be counted, and the register's
whole job is counting."

`lab` has the same failure mode and one extra consequence. **G-35** ("the lab has
no phone number — 'chase the lab' has no click") is still open, and the
`FollowUp` board exists more or less *because* somebody has to ring the lab about
Berisha's bridge on Thursday. The board knows the errand and cannot dial it.

A flat `Lab { name, phone }` — the same shape as `WorkProcedure`, with `WorkLine`
keeping its snapshot alongside the key, exactly as the services Bridge-A fix
did — closes G-35, makes "how much did we send to each lab this quarter"
answerable, and stops the spelling drift before the register has enough rows to
matter.

## What to do first

1. **`npm install` and commit the lockfile.** The image does not build. (§1.1)
2. **Add CI.** Four lines of workflow; it is what makes the rest of this list
   stop growing. (§1.4)
3. **Decide migrations or `db push`, and make all three places say the same
   thing.** Then write the missing migration. (§1.2, §1.3)
4. **Add `error.tsx`.** The app has no behaviour for its own failures. (§3.1)
5. **Audit the failed PIN, throttle the sign-in.** Two small changes to one
   file. (§2.1, §2.2)
6. **Test `patient-search`, `recalls`, `stock-consumption`.** The three untested
   modules whose bugs would be silent. (§5)

Everything after that is judgement rather than repair.
